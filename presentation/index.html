Architecture MVC
  • Modèle (Model) : Gère la logique du jeu, l'état des niveaux, des ennemis, des tours, du joueur, etc. (ex: LevelManager, GameManager, Player, Tower, Enemy).
  • Vue (View) : Affiche l'état du jeu à l'utilisateur via SFML. Chaque vue (ex: GameView, LevelView, TowerView, EnemyView, MainMenuView) se concentre sur le rendu d'un aspect du jeu.
  • Contrôleur (Controller) : Interprète les entrées utilisateur et modifie le modèle en conséquence (ex: TowerPlacementController gère le placement, l'amélioration et la vente des tours).
  • Séparation claire : Les vues n'accèdent jamais directement aux données du modèle, mais reçoivent des objets modèles à afficher. Les contrôleurs manipulent le modèle et déclenchent des mises à jour de la vue.
  • Extensible : Ajouter de nouveaux types de tours, ennemis ou vues est facilité par cette architecture modulaire.

Explication du fonctionnement
  • L'utilisateur clique sur une case de la grille pour placer une tour.
  • Le contrôleur (TowerPlacementController) intercepte l'événement et vérifie la validité de l'action (case constructible, ressources du joueur, etc.).
  • Si le placement est possible, le contrôleur modifie le modèle (LevelManager, Player, Tower), en ajoutant la tour et en mettant à jour les ressources du joueur.
  • Le modèle notifie la vue (GameView et ses sous-vues) qui se met à jour pour afficher la nouvelle tour sur la grille.
  • La séparation des responsabilités garantit que la logique métier, l'affichage et la gestion des entrées restent indépendants et facilement maintenables.

Design Patterns

State et Design Patterns
// --- State Pattern ---
// src/models/GameState.h
class GameState {
public:
  virtual ~GameState() = default;
  virtual void enter(GameManager &manager) {}
  virtual void update(GameManager &manager, float dt) = 0;
  virtual void handleInput(GameManager &manager) {}
  virtual void exit(GameManager &manager) {}
};

class MainMenuState : public GameState { /* ... */ };
class PlayingState : public GameState { /* ... */ };
// ... autres états ...

// Utilisation :
// GameManager possède un pointeur vers GameState et change d'état dynamiquement.

// --- Factory Pattern ---
// src/models/WaveManager.h
using EnemyFactory = std::function(const Path&)>;

class WaveManager {
  std::vector enemyFactories_;
  void setEnemyFactories(const std::vector& factories);
  // ...
};

// Utilisation :
// WaveManager utilise EnemyFactory pour créer dynamiquement des ennemis lors des vagues.
Explication des patterns
  • State Pattern : Permet de gérer les différents états du jeu (menu, jeu, pause, victoire, etc.) via une hiérarchie de classes dérivées de GameState. GameManager délègue le comportement courant à l'état actif, ce qui rend le code plus modulaire et extensible.
  • Factory Pattern : Permet la création flexible d'ennemis via des fonctions ou objets usines (EnemyFactory). WaveManager utilise ces factories pour instancier dynamiquement différents types d'ennemis selon la vague, facilitant l'ajout de nouveaux types sans modifier le code existant.
  • Ces patterns favorisent la séparation des responsabilités, la réutilisabilité et l'extensibilité du code.

Difficultés rencontrées

Extraits de code
// --- Passage des états texte vers UI ---
// Ancien :
if (state == "playing") {
  // logique du jeu en texte
}
// Nouveau :
class PlayingState : public GameState {
  void update(GameManager &manager, float dt) override { /* ... */ }
  void draw(sf::RenderWindow &window) override { /* ... */ }
};

// --- Migration SFML 2.6 -> 3.0 ---
// Ancien (2.6) :
window.draw(sprite);
// Nouveau (3.0) :
window.draw(sprite, states);
// Gestion des événements :
// sf::Event::Closed -> sf::Event::WindowClosed

// --- Gestion des projectiles ---
if (enemy->isAlive()) {
  projectile->setTarget(enemy);
} else {
  // On n'assigne pas la cible, le projectile est ignoré ou supprimé lors de la prochaine mise à jour
  projectile->markForRemoval();
}
Explications
  • Intégration des états UI : Le passage d'une version textuelle à une version graphique a nécessité la refonte du système d'états. Les états du jeu (menu, jeu, pause, etc.) sont désormais des classes dérivées de GameState avec des méthodes draw et handleEvent adaptées à l'UI SFML.
  • Migration SFML 2.6 → 3.0 : Plusieurs changements d'API (gestion des événements, signatures de méthodes draw, etc.) ont nécessité des adaptations dans tout le code, notamment pour la compatibilité avec les nouveaux types d'événements et les signatures de fonctions.
  • Projectiles et ennemis tués : Initialement, les projectiles pouvaient viser des ennemis déjà éliminés, causant des comportements indéfinis. Nous avons ajouté des vérifications (isAlive()) avant d'assigner ou de mettre à jour la cible d'un projectile, assurant ainsi la robustesse du système.

Perspectives et améliorations

Axes d'amélioration
  • Compléter l'intégration des assets (sprites, sons, polices) pour enrichir l'ambiance visuelle et sonore du jeu.
  • Ajouter de nouveaux types de tours et d'ennemis avec des comportements variés (effets de zone, ralentissement, boss, etc.).
  • Améliorer l'interface utilisateur et les animations pour une expérience de jeu plus fluide et attractive.
  • Refactoriser le code en séparant clairement les vues et les contrôleurs, en regroupant les fonctions utilitaires, en simplifiant la gestion des états, en clarifiant les interfaces entre modules et en documentant les dépendances entre classes.
  • Intégrer d'autres design patterns (Observer, Strategy) pour enrichir l'architecture, faciliter l'extension et la maintenance du projet.
